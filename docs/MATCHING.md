# MONOLOOP Matching Engine (Member 3)

The engine is explainable: it checks technical compatibility, finds the optimal multi-supplier allocation, and estimates delivered cost.

| Item | Location |
| :-- | :-- |
| Engine (pure TypeScript, no I/O) | `src/features/matching/` |
| API | `GET /api/matches/[requirementId]` |
| UI | `/matches`: live status of every open requirement. `/matches/[requirementId]`: full explanation, reached from **Find matches** on the demand page. |
| Tests | `src/features/matching/tests/` (`npm test`) |

---

## 1. Algorithm

The engine follows the four steps from the proposal (§7).

| Step | File | What happens |
| :-- | :-- | :-- |
| 1. Specification validation | `rules.ts` | Material family and grade must be recognised standards. Missing or invalid values **fail**; nothing is assumed compatible. |
| 2. Eligibility filtering | `rules.ts` | Every listing is checked against **every** mandatory rule (no short-circuit), so the UI can show a full pass/fail breakdown. |
| 3. Cost ranking | `costs.ts` | Estimated delivered cost = material + transport + handling. |
| 4. Allocation | `allocation.ts` | Optimal choice of suppliers and quantities. |

### Mandatory rules

A listing is compatible only if **all** of these pass:

| Rule | Requirement |
| :-- | :-- |
| Listing active | `status = ACTIVE`. Archived, completed or reserved listings are not offered. |
| Different organization | A buyer never sources from itself (relevant for hybrid organizations). |
| Material family | Exact. |
| Grade / specification | Exact. No substitution: SS201 ≠ SS304, standard ≠ marine plywood. |
| Length × width | Exact within 0.01 mm. **Either orientation**: a 1200×2400 sheet is a 2400×1200 sheet. Larger sheets are never cut down. |
| Thickness | Exact within 0.01 mm. |
| Condition | `ANY` accepts every condition; otherwise it must be equal. |
| Available stock | Uses `total − reserved` and **never** total stock. |

### Cost model (estimates, not quotations)

- **Material:** `unit_price × quantity`.
- **Transport + handling:** one charge **per supplier used**, `1,500 BDT + 60 BDT/km × road distance`, from the listing's city to the buyer's city. Distances between the demo cities are approximate, as listed in `costs.ts`. A pickup within the same city counts as 10 km; an unknown city pair uses a regional default of 150 km.

### Allocation (optimal)

The engine minimises the proposal's objective:

```
min  Σ pᵢ·xᵢ  +  Σ tₛ·yₛ        0 ≤ xᵢ ≤ availableᵢ ,  yₛ ∈ {0,1}
```

It decides in this order:

1. Fulfil as many pieces as possible.
2. Then minimise estimated delivered cost.
3. Then use fewer suppliers, then a deterministic ID order.

**Why it is exact.** For a fixed set of suppliers, taking the cheapest units first is optimal, because material cost is linear. Enumerating every supplier subset and filling cheapest-first therefore finds the global optimum. A typical requirement has only a handful of compatible suppliers, so this search is exhaustive up to 12 suppliers and falls back to a greedy method beyond that. A test compares the result against an independent brute force over every integer allocation on 300 random instances.

- `allow_split_suppliers = false`: each supplier is evaluated on its own (one supplier can still combine its own listings).
- Transport is charged once per supplier, so the engine adds a second supplier only when that is genuinely cheaper or necessary.

### Status and budget

| Status | Meaning |
| :-- | :-- |
| `EXACT_MATCH` | Full quantity from one supplier. |
| `MULTI_SUPPLIER_MATCH` | Full quantity from two or more suppliers. |
| `PARTIAL_MATCH` | Some quantity allocated; `unfulfilled_quantity > 0`. |
| `NO_MATCH` | Nothing compatible, **or** no budget-feasible allocation. |

The budget is the requirement's **total** `maximum_budget_bdt`, compared with the **delivered** cost. For partial fulfilment the budget is prorated (for example, 30 of 60 pieces allows half the budget). When even the cheapest option exceeds the budget:

- the status is `NO_MATCH` and `allocations` is empty;
- `budget.status = 'OVER_BUDGET'`;
- the rejected cheapest option is returned in `over_budget_alternative` so the UI can explain it.

## 2. Evaluation against a name-only search

The dataset is in `src/features/matching/evaluation/dataset.ts`: 35 listings, 12 requirements and 8 fictional organizations. It contains deliberate traps (grade, thickness, size, condition, fully reserved, archived, the buyer's own stock) and requirements that need stock from several suppliers. The ground truth is labelled **by hand** from the material rules, not generated by the engine.

The baseline (`baseline.ts`) imitates a conventional marketplace search: it matches family and grade **name** only and counts total stock as available.

To print the table:

```bash
npx vitest run src/features/matching/tests/evaluation.test.ts --silent=false
```

| Metric | MONOLOOP | Name-only baseline |
| :-- | :-: | :-: |
| Compatibility precision | **100.0%** | 28.9% |
| Compatibility recall | 100.0% | 100.0% |
| Listings suggested (total) | 24 | 83 |
| Requirements reported fulfilled (truth: 9) | **9** | 12 |
| False "fulfilled" claims | **0** | 3 |
| Quantity allocation errors (pieces) | **0** | 650 |

Estimated delivered cost of MONOLOOP's fulfilled requirements: 1,367,700 BDT.

The baseline suggests 3.5× more listings, and 71% of them are unusable. It also tells buyers that 3 requirements can be fulfilled when they cannot (not enough stock, or over budget), and it would allocate 650 pieces from incompatible or reserved stock.

## 3. API contract (for Member 4)

`GET /api/matches/[requirementId]` returns `ApiResponse<MatchResult>`.

| Status | Meaning |
| :-- | :-- |
| 200 | `MatchResult` |
| 404 | `NOT_FOUND` |
| 409 | `REQUIREMENT_NOT_OPEN` (cancelled or fulfilled requirements are not matched) |
| 500 | `INTERNAL_ERROR` |

`MatchResult` **extends** the frozen `MatchProposal` in `src/lib/types.ts`, so every contract field is present:

- `allocations[]`: `listing_id`, `supplier_organization_id`, `supplier_name`, `allocated_quantity`, `unit_price_bdt`, `subtotal_bdt`, `city`, `technical_notes`. Each one also has `estimated_transport_bdt` and `distance_km`.
- `listing_ids` and `allocated_quantities` cover **allocated** listings only.
- `compatible_supplier_ids` lists **all** technically compatible suppliers, not only the ones allocated.
- `estimated_material_costs_bdt`, `estimated_transportation_costs_bdt` and `total_estimated_cost_bdt`.
- `compatibility_explanations[]`, `rejection_reasons[]` and `unfulfilled_quantity`.

The extra fields (`evaluations`, `budget`, `baseline`, `allocation_method`, `over_budget_alternative`) can safely be ignored.

Server-side use without HTTP:

```ts
import { matchRequirement } from '@/features/matching/services/matching.service';
const outcome = await matchRequirement(requirementId); // { kind: 'OK', result } | NOT_FOUND | NOT_OPEN
```

> **A proposal is not a reservation.** Stock can change between matching and acceptance, so the exchange module must re-check `available_quantity` atomically (with `reserve_listing_quantity`) when each supplier accepts.

**Request exchange button:** the matches page shows a disabled **Request exchange** button in `MatchResultsView.tsx` (`ActionBar`). Once `POST /api/exchanges` exists, we wire it to send `{ requirement_id, allocations }` from the `MatchResult`.

## 4. Integration notes

- **Requirements:** read through Member 2's `requirementRepository.getRequirementById` (`src/features/demand/services/requirementRepository.ts`). Numeric fields are coerced to numbers before matching.
- **Listings:** read through Member 1's `listingRepository.getListings({ materialFamily })`. The engine sees live reservations.
- **Styling:** the `/matches` page uses its own scoped visual language (`components/theme.ts`, based on usealia.com). It does not change the shared Tailwind config or layout.
